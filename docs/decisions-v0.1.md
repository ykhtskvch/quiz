## A. Блокирующие

### D-01 — Культурный бэкграунд игрока не собирается

**Проблема.** Движку нужен `cultural_contexts[]` каждого игрока (Engine §3.1, §7 Cultural Match). Но ни в одном документе onboarding его не спрашивает: нет ни BR, ни US-ONB, ни поля в API §10, ни таблицы в ERD. Без этого движок не знает, кто в комнате вырос в постсоветском пространстве, а кто в UK. Russian Mode и International Mode фактически не работают.

**Где:** Vision §7, BR §3, US-ONB-*, ERD §6–7, API §10.

**Варианты:**
- (a) Явный приватный шаг «С какой культурой ты вырос(ла)?» — multi-select карточек (Post-Soviet, UK, US, Western Europe, Asia, …).
- (b) Выводить из выбранных тем: «Фабрика звёзд» означает POST_SOVIET.
- (c) Комбинация: шаг (a) необязателен, а при пропуске срабатывает вывод (b).

**Рекомендация:** (c). Добавить BR, US-ONB-008, таблицу `PLAYER_CULTURAL_CONTEXT (onboarding_id, cultural_context_id, strength)` и поле в payload onboarding.

**Решение:** ✅ (c) — необязательный приватный шаг «С какой культурой ты вырос(ла)?» + вывод из тем при пропуске.

### D-02 — Режим игры и язык смешаны

**Проблема.** «International Mode / Russian Mode / Mixed Mode» описывают одновременно язык (на каком языке вопросы) и культурный слой (чью культурную память задействуем). Из-за этого непонятно, что видят британец и русскоязычный игрок в одной комнате. В модели есть только `ROOM.default_language`, поля режима нет.

**Где:** Vision §5, BR-033–037, ERD §3.

**Варианты:**
- (a) Режим — это только **язык комнаты** (EN / RU). Культурный микс определяется профилями игроков (D-01), а не режимом.
- (b) Оставить три режима как явный выбор хоста: язык + набор допустимых контекстов.

**Рекомендация:** (a). Термины «International / Russian Mode» уходят из спецификации или остаются только маркетинговыми. Следствие: вопрос про «Куклы» в EN-комнате — это отдельный `QUESTION` на английском с тем же `fact_id`. Нужен BR про то, какие контексты допустимы в EN-комнате и требуется ли перевод.

**Решение:** ✅ (a) — режим = только язык комнаты; культурный микс — из профилей игроков.
**Дополнительное правило:** культурно-специфичный вопрос (например, POST_SOVIET) не переводится на другой язык. Перевод допустим только для GLOBAL / bridge-вопросов; специфичные вопросы существуют только на «родном» языке своего контекста. → новое поле `QUESTION.translatable` (или правило по `culture_specificity`), фильтр в Eligibility.

### D-03 — Граница MVP

**Проблема.** В приоритетах (FR-doc §6, P0) нет ничего, что отличает продукт: Hero Moment, Cultural Dignity и культурные контексты стоят в P1. В backlog это частично исправлено (волна 2), но метки остались P1. Если проверять Play Again Intent на P0, проверяется обычный квиз с подбором по интересам, а не сама идея.

**Где:** FR-doc §6, Backlog §36.

**Рекомендация.** MVP = волна 1 плюс минимальное ядро отличий:

| Входит в MVP | Не входит |
|---|---|
| Room, QR, nickname, onboarding (+ D-01) | Late join, reconnect за пределами refresh |
| Composition: фильтр → score → top-N → weighted random | Audio, video, rights workflow |
| `hero_need` (минимальная версия) | AI pipeline, admin portal |
| Cultural Dignity: score вопроса + медиана комнаты | Gold, semantic dedup |
| Cultural context теги + профиль | Автокалибровка сложности |
| Text + image вопросы (только свои / PD картинки) | Donation |
| Reveal, распределение, scoring, final leaderboard | Accessibility beyond basics |
| Pause, Skip, End (см. D-15) | |
| Play Again Intent + difficulty feedback + Great/Bad | |
| Банк в JSON / таблице в репо | |

**Решение:** ✅ согласна с рекомендацией — волна 1 + минимальное ядро отличий (таблица выше).

### D-04 — Нет потока работ по наполнению банка

**Проблема.** Персонализация бесполезна без банка, размеченного по нишам, языкам, сложности, Dignity и контексту. В backlog есть хранение банка, AI pipeline (волна 4) и редакторский процесс, но никто не описывает, **кто и как создаёт первые вопросы к волне 2**.

**Грубая оценка для MVP (один язык):**
- игра ≈ 25 вопросов, Play Again удваивает: ≥ 50 уникальных фактов на комнату;
- окно top-15 на каждом шаге и фильтры требуют пула в несколько сотен eligible-вопросов;
- Hero Moment требует ≥ 3–5 вопросов на каждую нишевую тему, которую игрок может отметить как Expert.

Итого ориентир — **300–500 вопросов**: ~30 тем по 10–15 вопросов плюс ~100 wildcard / shared.

**Варианты производства:** только вручную; AI-драфт с твоей проверкой; AI-драфт с проверкой по источникам и выборочной ручной проверкой.

**Рекомендация:** AI-драфт с обязательной ручной проверкой, формат — структурированный JSON/YAML в репо по схеме из ERD. Добавить **EPIC «Content Production»** с целью «банк для MVP» и поставить его параллельно волне 1, а не в волну 4. Сузить taxonomy на старте до тем, под которые есть контент.

**Решение:** ✅ AI-драфт с обязательной ручной проверкой; ориентир 300–500 вопросов принят; EPIC «Content Production» параллельно волне 1.
**Первый язык:** русский. **Темы:** предлагает Claude → `spec-v0.2/08-topics-mvp.md`.

### D-05 — Два разных алгоритма построения последовательности

**Проблема.** Engine §21 описывает **шаблон слотов** («1. Easy + Shared, 2. Medium + cultural memory, …»). Engine §43 и API §58 описывают **жадный выбор**: следующий вопрос на каждом шаге. Это разные архитектуры.

**Рекомендация:** жадный выбор по шагам (§43). Он нужен для late join, skip и адаптации. Шаблон §21 понизить до иллюстрации желаемого результата. От шаблона оставить только жёсткие правила для первых 2–3 вопросов (§22) и guardrails (§42).

**Решение:** ✅ согласна — жадный выбор по шагам.

### D-06 — Конфликтующие целевые распределения

**Проблема.** Одновременно заданы:
- доли состава (§35);
- микс Knowledge Effects (§15);
- кривая сложности (§36);
- распределение Dignity (§37);
- минимальная доля поколений (§27);
- формула score (§17);
- штрафы (§18).

На 25 вопросах и небольшом банке они неизбежно конфликтуют, а порядок уступок не определён.

**Рекомендация — порядок приоритета (сверху вниз, нижние уступают верхним):**
1. Eligibility / safety (minors, rights, retired) — жёстко.
2. Дедупликация `fact_id` — жёстко.
3. Ограничения первых вопросов — жёстко.
4. Покрытие Hero (каждый игрок ≥ 1) — сильный boost.
5. Целевая сложность (accuracy 50–70 %).
6. Diversity penalties.
7. Распределение Dignity.
8. Микс Knowledge Effects.

Пункты 5–8 — **мягкие цели**. Они влияют на score и измеряются постфактум (Engine §41), но не работают как квоты.

**Решение:** ✅ согласна — порядок приоритета как в рекомендации.

### D-07 — Сложность для комнаты на холодном старте

**Проблема.** Пример с «Куклами» (из 3/5 в 2/5) требует либо статистики по похожим комнатам, которой в начале нет, либо явного правила.

**Рекомендация (стартовое правило):**
`room_difficulty = global_difficulty − 0.5 × (доля игроков с LIKE по теме или совпадающим cultural context)`, с ограничением [1; 5]. Если ни у кого нет совпадающего контекста, а вопрос не wildcard и не bridge, вопрос не eligible. Коэффициенты конфигурируемые (NFR-015).

**Решение:** ✅ согласна — стартовое правило как в рекомендации.

---

### D-08 — Когда создаётся первая GAME_SESSION

**Проблема.** `POST /rooms` создаёт только Room, а onboarding отправляется на `/games/{gameSessionId}/...` (API §10). Игрок проходит onboarding до того, как появляется сессия.

**Рекомендация:** Room создаётся сразу вместе с первой GAME_SESSION в статусе `ONBOARDING`. Play Again создаёт следующую.

**Решение:** ✅ согласна — первая GAME_SESSION создаётся вместе с Room.

## B. Продуктовые правила

### D-09 — Имена в статистике конца игры

**Проблема.** Движок намеренно даёт каждому игроку примерно один вопрос «под него» (Engine §38). Плашка «Only one person knew this» с именем фактически раскрывает интерес. В API §40 `onlyOneKnewQuestionId` уже без имени, а `fastestCorrect` — с именем.

**Рекомендация:** зафиксировать BR. Статистика, указывающая на одного игрока через вопрос (Only One Knew), — без имени. Статистика, не связанная с темой (Fastest Correct), — с именем.

**Решение:** ✅ согласна — Only One Knew без имени, Fastest Correct с именем.

---

### D-10 — Skip: баллы и момент нажатия

**Проблема.** BR-087: баллы не начисляются. API §32: «не учитываются **либо** аннулируются». Не определено, можно ли нажать Skip во время ANSWERING и после частичных ответов.

**Рекомендация:** Skip доступен в PRESENTING и ANSWERING. Все ответы на вопрос аннулируются, никто не получает баллов. Факт считается использованным (API §33).

**Решение:** ✅ согласна — Skip в PRESENTING и ANSWERING, все ответы аннулируются, факт использован.

---

### D-11 — End Game: в любой момент или на границе вопроса

**Проблема.** BR-009: в любой момент. US-013: на границе вопроса.

**Рекомендация:** в любой момент. Если текущий вопрос ещё не прошёл reveal, он аннулируется как Skip.

**Решение:** ✅ согласна — в любой момент, неоткрытый вопрос аннулируется как Skip.

---

### D-12 — Минимум игроков и маленькие комнаты

**Проблема.** BR-003 задаёт целевые 4–8, но минимум для Start не определён (API §11). В комнате на 2–3 человека агрегированное распределение ответов почти раскрывает, кто что ответил.

**Рекомендация:** Start возможен с 2 игроков. При < 4 активных игроках отключать плашки статистики, указывающие на одного человека.

**Решение:** ✅ согласна — старт с 2, плашки «на одного» отключаются при < 4.

---

### D-13 — Шкала Cultural Dignity в onboarding

**Проблема.** Engine работает со шкалой 1–5 и медианой. Что видит игрок, не определено (OBR, Vision §39 п. 6).

**Рекомендация:** игроку показывать 3 варианта с человеческими формулировками (примерно «больше классики / баланс / больше поп-культуры и ностальгии»), внутри маппить на 4 / 3 / 2. Финальный текст — через UX-тест.

**Решение:** ✅ согласна — 3 варианта, маппинг 4 / 3 / 2.

---

### D-14 — Late joiner и Hero boost

**Проблема.** Новый игрок получает `hero_need = 1.0` (Engine §31). Если в комнате все уже покрыты, следующие вопросы могут подряд уйти «под него».

**Рекомендация:** для late joiner ограничить boost: не раньше чем через 2 вопроса после входа и не более одного hero-кандидата в окне из 5 вопросов.

**Решение:** ✅ согласна — ограничение boost для late joiner.

---

### D-15 — Pause и Skip в MVP

**Проблема.** Pause и Skip стоят в P1, но описаны как базовые controls хоста (BR-005). Skip — ещё и сигнал качества, нужный с первого дня.

**Рекомендация:** перенести Pause, Resume и Skip в P0 и MVP. Они дешёвые.

**Решение:** ✅ согласна — Pause, Resume, Skip в P0.

## C. Технические (рекомендация по умолчанию)

**Решение:** ✅ все T-01…T-10 приняты.

| ID | Проблема | Предлагаемое решение |
|---|---|---|
| T-01 | Жизненный цикл вопроса описан в 4 разных вариантах. GOLD — и статус, и `gold_status` boolean. | `DRAFT → FACT_CHECKED → APPROVED → GOLD`, `RETIRED` из любого состояния. PLAYED / PROVEN — не статусы, а производные из QUESTION_STATS. Источник (AI / human) хранится в `generation_method`, поэтому GENERATED не нужен. Убрать `gold_status`. |

| T-04 | `ACTIVE_FROM_NEXT_QUESTION` нет в enum. Presence и PLAYER.status расходятся. | `PLAYER.status = PENDING / ACTIVE / DISCONNECTED / LEFT`. ANSWERED — состояние ответа на вопрос, а не игрока. |
| T-05 | Машина состояний (API §52) смешивает статусы Room и GameSession. | Две отдельные машины: Room (WAITING / ACTIVE / CLOSED / EXPIRED) и GameSession (ONBOARDING / ACTIVE / PAUSED / FINISHED / ABORTED). |

| T-07 | Состояние движка (`hero_need`, `recent_topics`, `hero_opportunities`) негде хранить. | `GAME_SESSION.composition_state JSONB`, чтобы пережить рестарт сервера. |
| T-08 | Код из 5 символов без rate limiting легко перебрать. | 6 символов без похожих (0/O, 1/I), rate limit на join / reconnect, токены — только как hash в БД (уже так). |
| T-09 | Пул кандидатов: 8–10 (API §13) против 3–5 (API §59). | Одно конфигурируемое значение `prefetch_size`, по умолчанию 5. |
| T-10 | В фильтре (Engine §6) исключаются чужие контексты, а Engine §29 хочет cross-cultural вопросы. | Ввести явный признак `bridge` / `guessability`: такие вопросы проходят фильтр контекста. |
